## 真机反馈修复（用户报告：点启动无任何反应）→ v1.0.1
用户实测：「只申请 VPN 权限，同意后点启动提示『正在启动』然后没反应」。
根因分析（对照官方文档核实）：
1. **VPN 配置非法**：原用 `addAddress(10.111.222.1, 32)` + `addRoute(10.111.222.2, 32)`——路由目标地址不在接口网段内，官方示例与大量实践均为「接口 /24 + 覆盖同网段的路由」。部分 ROM 会拒绝该路由导致 `establish()` 失败。
2. **失败被静默吞掉**：`builder.establish()` 的异常被 `catch { null }` 吞掉，返回 null 后直接 `stopSelf()`，UI 无任何反馈 → 表现为"点了没反应"。
3. **启动顺序风险**：原先是 establish() → startForeground()，而 `startForegroundService()` 要求 5 秒内调用 startForeground()。
修复内容（v1.0.1 / versionCode 2）：
- 配置改为 `addAddress(10.111.222.1, 24)` + `addRoute(10.111.222.0, 24)` + `addDnsServer(10.111.222.2)`（新常量 DNS_SUBNET / TUN_PREFIX）
- `startForegroundInternal()` 提到 establish() 之前，并 try/catch（失败记「前台服务启动失败」）
- 新增 `DnsStats.lastError` + `onVpnError()/clearLastError()`，statusJson 增加 `state`/`lastError` 字段
- UI：状态 pill 新增 `.pill.error`（红色「启动失败」），run-meta 显示失败原因并 toast 一次；重试/停止时清错误
- `writePacket` 写入失败也会记录（隧道静默失效可见）
- `onStartCommand` 支持 START_STICKY 重启（null intent + 仍持授权 + 最多 3 次）
- MainActivity/WebAppInterface 的 startForegroundService 异常也接入同一条错误通道；移除 onActivityResult 里过早的 "vpn_started" 提示
- 已核实：Android 14 `specialUse` 前台服务 property 名 `android.app.PROPERTY_SPECIAL_USE_FGS_SUBTYPE` 正确，无需改动
交付：dist/ 更新为 DNSSwitch-1.0.1-{debug,release}.apk + source.zip（33 个单测仍全绿，Release v2 签名与 1.0.0 同一证书，可覆盖安装）

## 三轮真机反馈破案 → v1.0.3（真正的根因）
用户发回 1.0.2 日志页 4 条「系统」条目（全部同一秒）：收到启动指令 → 前台服务已就绪 → **VPN 接口已建立** → **隧道读循环退出（读…）**。
**结论：establish() 一直是成功的**，前两轮修的都不是病灶；真正根因（联网核实，官方 setBlocking() 文档原文背书）：
> **establish() 返回的 TUN fd 默认是非阻塞模式**（"By default, the file descriptor returned by establish() is non-blocking"）。
读循环第一次 read() 时队列无包 → 非阻塞 fd 立即抛 EAGAIN → 旧代码 catch{break} → 1 秒内服务自拆。这正是「点了启动没反应」的完整解释（接口起来了又瞬间没了，且无任何错误通道触发）。
v1.0.3 / versionCode 4 修复：
1. **Builder 加 `.setBlocking(true)`（根治）**——读循环按阻塞语义设计；builder 构造也并入 establish 的 try（任何一步异常都有留痕）
2. **读循环韧性重写**：EAGAIN/"Try again" 类异常 → sleep(50) 退避重试不退出（防个别 ROM 无视 setBlocking）；其他异常连续 20 次才判死（首次失败即写「系统」日志含完整原因）；read<0 同样计数；read==0 按瞬时抖动
3. **onRevoke 留痕**（区分「系统撤销 VPN」与「读失败」两种死法）
4. **日志页「系统」条目完整显示**：`.log-row.sys` 取消单行截断（word-break 换行）——上轮诊断信息被 CSS ellipsis 截断差点又浪费一轮
5. 33 单测全绿；Release 同证书 v2 签名，versionCode 4 可覆盖安装
**经验**：真机问题务必先上「步骤级留痕」再修——三轮才定位到，若第一版就有系统日志，一轮就能破案

## v1.1.0：自定义预设 + txt 导入 + IPv6 分别设置（20:46）
用户新需求三点：① 自定义 DNS/DoH/DoT 可「存为预设」；② 支持分别设置 IPv4 / IPv6 的 DNS 地址；③ 支持 txt 文件批量导入（行格式 `地址 名字 分类`，分类不区分大小写）。

实现（versionCode 5 / versionName 1.1.0，单测 61 个全绿）：
1. **配置模型**（AppConfig.kt）：TraditionalConfig / DotConfig 各加 `serverV6`；`Validators` 拆出 isIpv4 / isIpv6 / isHostname / isHostOrIp。IPv6 校验收紧：无 `::` 时必须正好 8 组，含 `::` 时两段合计 ≤7 组且只允许一处压缩，末组可为点分 IPv4（`::ffff:1.2.3.4` 计 2 组）。旧配置缺 serverV6 字段按空串兼容。
2. **预设模型**（新增 `config/DnsPreset.kt`）：`DnsPreset` + `PresetType`(dns/doh/dot) + `ImportReport` + `PresetLogic`（纯逻辑，可 JVM 单测）。行解析：分类取**行末 token**（不区分大小写），名字是中间所有 token（可含空格）；省略分类时按地址形态推断（http(s)→DoH、IP→传统 DNS、其他主机名→DoT）；**同「分类+名字」合并**，故 IPv4 行与 IPv6 行合成一条。
3. **持久化**（新增 `config/PresetManager.kt`）：SharedPreferences `dnsswitch_presets` 存 JSON 数组，与 ConfigManager 分开。
4. **bootstrap 解析**（新增 `dns/Bootstrapper.kt`，**关键架构修复**）：VPN 启动后系统 DNS 被自身接管，域名型 DoH/DoT 上游若走系统解析器解析自身主机名会死循环。改为用 protected socket 向传统 DNS 直发原生 A/AAAA 查询（引导服务器是 IP 字面量，环路断开），带 60s 缓存；OkHttpClient 挂 `BootstrapDns`；DoT 填主机名时设 SNI + 证书主机名校验，填 IP 时跳过。
5. **通道 IPv6 备用**：TraditionalDnsChannel 先 v4 后 v6；DotChannel 支持主机名解析 + v6 备用 + SNI。
6. **前端**：三张通道卡片各加 IPv6 输入框 / 自定义预设 chips / 「＋存为预设」「管理预设」；新增预设管理 modal（分类筛选 + 列表应用/删除 + txt 文件导入 + 粘贴导入）与命名 modal（不用 JS prompt，WebView 默认不弹窗）。txt 文件由 `MainActivity.onShowFileChooser` → `onActivityResult` 读（UTF-8 优先，出现 U+FFFD 回退 GBK）→ `window.onPresetFileLoaded(text)` 回传 JS。
7. **桥接**：WebAppInterface 增 getPresets / importPresetText / addPreset / deletePreset。
- 单测新增：PresetLogicTest 15 例、AppConfigTest IPv6/主机名 9 例、DnsMessageTest buildQuery/AAAA/formatIpv6 4 例。
